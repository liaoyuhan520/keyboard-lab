## 2. 存储位置与体积策略

选择 `data/idioms.db`，而不是 `public/`：

- `data/` 是构建期数据源，Vite 不会把它打进主包，也不会作为静态文件发布。
- 如果把 SQLite 放进 `public/`，浏览器既不能直接读取，还会额外分发约 30 MB 的不可用文件。
- 构建脚本从同一个数据库生成成语候选词库 `src/data/hanziIdiomLexicon.ts`，以及释义模块 `src/data/hanziIdiomDefinitions.ts`。
- 成语候选词库继续按需加载；释义模块只被动态 `import()`，只在用户选中成语时加载。
- 拼音匹配逻辑保持不变：候选词仍以精确、无调拼音为索引；模糊匹配和词频排序只追加候选或调整候选顺序，不改变精确键。
- 浏览器运行时没有新增 SQLite、Node 或 WASM 依赖；`sql.js` 只在构建期使用。

## 3. 字段优先级与多释义处理

导出优先级：

1. `brief`（简明释义）
2. `brief` 为空时使用 `detailed`
3. 两者都为空时不导出，运行时显示“暂无释义”

显示方式：

- `brief` 作为主释义直接展示。
- `detailed` 存在且与主释义不同，放在可折叠的“详细释义”中，避免默认撑长卡片。
- 数据库一个成语一条主记录，同一记录内的多义项保留原文；包含编号的释义按原文展示。
- 不采用数据库中的 `pinyin` / `zhuyin` 做匹配，拼音匹配继续以现有成语词库为准，避免多音字和排序回归。
- 候选词库同样以 `data/idioms.db` 的四字及以上记录为唯一来源；生成时用 `pinyin-pro` 生成拼音，确保与现有精确拼音输入方式一致。
- 释义中的 HTML 标签、HTML 实体和多余空白在构建期清理。

## 4. 降级行为

- 某条成语查不到释义：显示“暂无释义”，朗读和逐字笔顺照旧。
- `hanziIdiomDefinitions` 动态模块加载失败：显示“释义暂时无法加载，仍可朗读和查看逐字笔顺”，不白屏。
- `data/idioms.db` 缺失或读取失败：导出脚本生成空定义模块并输出警告；页面退回原有不带释义的行为。
- 成语词库本身加载失败或为空：仍保留普通词和单字候选，不白屏；释义不可用，朗读和笔顺不受影响。

## 5. 生成流程

```bash
npm run generate:hanzi-idioms
npm run generate:hanzi-idiom-definitions
```

脚本：

- `scripts/generate-hanzi-idioms.mjs`：从 `data/idioms.db` 读取四字及以上词条，用 `pinyin-pro` 生成拼音并输出候选词库。
- `scripts/generate-hanzi-idiom-definitions.mjs`：从同一个数据库导出 `brief` / `detailed` 释义。

输出：

- `src/data/hanziIdiomLexicon.ts`
- `src/data/hanziIdiomDefinitions.ts`（约 2.68 MB 源码，Vite 按需分块）

构建期使用的 `sql.js` 为 devDependency，不进入浏览器产物。

## 6. 模糊候选规则

精确匹配保持原样：先按无调拼音做 `Map` 精确查询；候选排序再把精确命中放在模糊命中之前。

模糊规则只在精确命中之外追加，不会改变精确索引：

- 输入长度至少 6 个字母才启用模糊匹配。
- **前缀匹配**：输入长度至少 8 个字母，且词条拼音键以输入开头。
- **编辑距离**：输入 6–11 个字母允许 1 次编辑；输入 12 个字母及以上允许 2 次编辑。采用 Damerau/OSA 距离，支持替换（含相邻键错拼）、插入（多字）、删除（漏字）和相邻字符交换。
- 模糊结果按“前缀 < 1 次编辑 < 2 次编辑”排序，再按词频、字数和词库原顺序稳定排序；每个来源的模糊结果数量按输入长度自适应：6–8 个字母最多 3 条，9 个及以上最多 6 条。
- 模糊候选在拼音前显示 `≈`，卡片使用虚线边框；精确候选不显示该标记。
- 模糊只对已加载的成语库和 HSK 普通词索引生效；不会为 `gongyuan` 触发成语库加载。普通词的模糊候选从 6 个字母起可计算，成语库仍按原按需条件在输入达到 8 个字母且没有单字候选时加载。实现见 [src/data/fuzzyPinyin.ts](../src/data/fuzzyPinyin.ts)。

## 7. 候选排序与词频

对标场景：Windows 11 微软拼音的桌面中文单词/短语候选，不包含整句上下文联想、云端个性化词库和用户自学习。

- 词频来源：SUBTLEX-CH-WF（`subtlex-ch-wf`，MIT）的 `WCount`。构建时写入词库元组第四个字段，运行时只读取已生成的静态数据，不新增运行时依赖。
- 普通词和四字及以上成语使用同一套排序键：
  1. 精确命中永远在模糊命中之前；
  2. 模糊命中的编辑距离/前缀等级更优者在前；
  3. 词频降序；
  4. 同频时字数更多者优先（长词优先的有限实现）；
  5. 最后保持词库原顺序。
- 单字候选仍按 SUBTLEX-CH-CHR 字频排序，并排在词语候选之后。
- 没有实行“所有长词一律优先”：这会压过高频常用词，反而不像真实输入法。长词只在同频时作为次级排序。
- 没有引入用户输入历史、云端词频或上下文学习。

## 8. 已知数据质量限制

释义来自用户提供的抓取库，保留了源数据的部分用字、标点和释义表述。本集成只做 HTML/空白清理，不改写释义内容；因此个别条目的释义可能存在源站自身的错别字或缺字。

数据库中的三字及以下条目仍不导出；四字及以上已支持。少数四字以上条目因 `pinyin-pro` 无法生成四个及以上合法音节或拼音键超过 24 字母，只导出释义、不进入候选，共 29 条。
